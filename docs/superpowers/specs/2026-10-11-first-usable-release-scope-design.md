# FactsPDF 首个可用版本：范围与验收草案

日期：2026-10-11  
版本：范围草案 0.1，不是软件发布版本  
审阅基线：M12 合并提交 `1e3f24f21b2e9bbdc5db6e05066998c07a6f9af6`  
状态：用户已接受“先回顾、定义首版，再安排里程碑”的方向；本稿中的具体场景、格式和平台组合是供审阅的新建议，不是已完成或已批准的功能。

本次只提交规划文档，不修改引擎、测试、工作流、依赖、公共 API 或许可，不启动原先建议的 M13 文本编码优化。范围稿审阅后，再为第一个有明确验收标准的工作项编写实施计划。产品范围不是一个需要一次完成的大 PR。

## 1. 已确认方向与事实基线

保留一套无浏览器排版依赖的核心，输入使用标准 HTML 和明确支持的 CSS 子集；不同语言通过适配层接入同一引擎。快速启动、低资源占用、AOT 和跨平台是工程目标，需要分别提供实际证据。不会因为 Windows/macOS 测试通过，就宣布这两个平台的 Native AOT 或 WASM 已交付。[S1][S2]

当前已有库 API、CLI、显式 TrueType 字体与简单横排 Unicode/中文、字体子集、嵌套块级布局、背景/实线边框和跨页片段。当前文档仍将列表、链接、粗体/斜体元素、图片、表格、完整页眉页脚和其他语言绑定列为未支持或未实现。现有字体支持不代表完整文本塑形、双向排版或所有文字系统。[S1][S2]

M9–M12 的资源控制和分配优化继续作为回归基线。它们不构成全流程流式处理、恒定内存或峰值进程内存保证。此前长段落分配结果与端到端基准必须分开；后者保留原始固定基线，不能悄悄改名为新的版本对照。[S3]

后续的基本决策单位改为：用户获得的能力、可检查的交付物、验收门槛与明确排除项。Mxx 编号仅用于跟踪，不再因为发现一个可以优化的函数就自动创建下一阶段。

## 2. 推荐首版定位与用户旅程

建议将首个可用版本称为 **Developer Preview 1**，表示受控场景开发者预览，不表示 1.0、稳定公共 API、生产 SLA 或已获准公开发布。

**主要场景：中英双语业务报告。** 报告需要标题、摘要、重点段落、列表、信息面板、少量静态图片、固定列宽的明细表，以及可预测的多页输出。不将此场景绑定到某个房地产或其他业务项目；测试内容采用合成数据。

单据和图文说明书作为扩展验收样本，不同时扩展成财务计算引擎或通用出版系统。模板填充与业务计算由调用方完成，FactsPDF 接收已经生成的 HTML、CSS 和显式资源，负责排版与 PDF。

目标用户旅程：取得指定构建 → 使用清晰的 CLI 或 .NET 示例 → 提供 HTML/CSS 与显式字体/图片 → 生成可搜索、可复制、可阅读的 PDF → 对不支持的输入获得可定位错误。第三方接入者应能只按文档复现，不需要作者手工修改仓库或提供隐藏配置。

### 路线取舍

- **推荐：报告场景驱动，较早验证接入风险。** 用真实输出确定补哪些功能，同时避免最后才发现 WASM 或其他宿主需要不同资源边界。
- 暂不采用“继续性能优化直到足够快”：尚未解决用户无法表达列表、图片、明细表的问题。
- 暂不采用“一次发布所有语言与平台”：没有充分运行证据时，会放大维护面并延迟一个可用入口。

## 3. 建议的首版能力边界

下面是候选发布范围，不是当前支持声明。每个新子系统在实施前仍需要自己的小范围设计。

| 能力 | Developer Preview 1 建议范围 | 明确排除或后续处理 |
| --- | --- | --- |
| 已有排版 | 保留现有 HTML/CSS 子集、Unicode/中文、块级布局与跨页绘制 | 任意网页截图或完整浏览器兼容 |
| 强调文字 | 显式提供常规与粗体字体，定义真实字体角色映射和缺失时的错误；不伪造粗体 | 任意字体自动发现、复杂字体匹配与所有粗细轴；斜体另行排期 |
| 列表 | 有序十进制列表、无序列表，最多两级嵌套，标记与正文换行/分页正确 | 任意计数器、自定义标记图片与完整列表 CSS |
| 图片 | 第一批限定显式提供的静态 JPEG，保持纵横比，定义资源与解码边界 | PNG 为后续独立阶段；首版不承诺透明图、SVG、动画、自动 URL 抓取 |
| 表格 | 明确列宽、分离边框、单元格文字换行；跨页按整行移动，重复表头 | 自动列宽求解、跨行/跨列单元格、嵌套表格、跨页拆分一个单元格；单行高于可用页面时明确拒绝 |
| 分页体验 | 保留显式分页；增加一个明确的标题随首段策略、受控页眉/页脚与页码 | 完整 @page、任意页内浮动、脚注、通用孤行寡行算法 |
| 错误与资源 | 明确支持矩阵、可用时给出源位置、资源额度和失败前不输出 | 把此能力称为完整恶意输入沙箱 |

JPEG 优先是缩小首批图片功能面的建议，而不是说解码不需要设计与安全检查。若首批报告必须使用透明 Logo，应该在范围审阅时用 PNG 替换或扩展该项，并记录其成本，不能在实施中静默增项。

新图片能力必须为压缩数据长度、尺寸、像素数、解码后大小、色彩/方向处理和取消操作设界限；没有可验证的解码方案时，不得通过放宽资源限制来声称完成。默认不增加新的运行时依赖，任何确有必要的例外单独审阅。

真实字体角色映射可能需要扩展调用方的资源描述。现有调用保持兼容；本稿不提前发明 API 名称或承诺其已冻结。

## 4. 接入方式与平台边界

**第一条交付路径建议为 CLI + .NET 库。** 包制作、安装验证和公开发布分开：可以先验证本地产物，但公开 NuGet/npm/二进制发布仍需通过仓库已有发布门槛及明确授权，不因范围文档通过而自动发布。[S1][S2]

建议首发 Native AOT 运行目标为 **Linux x64 与 Windows x64**。Linux 已有实际证据，Windows AOT 在当前基线仍是新增目标，必须真实构建、运行和检验输出后才能宣称支持。macOS 继续保留现有测试，但 macOS arm64 AOT 发布组合放入后续计划，不能混称已验证。

较早执行两个范围受限、顺序开展的可行性验证，不等于同时启动两个产品项目：

1. TypeScript/Node 通过 CLI 接入同一核心，验证 UTF-8 输入、二进制 PDF 输出、显式资源、退出码、超时/取消和并发隔离。此路径应如实标为子进程适配，不称为原生内存调用或已发布 SDK。
2. 浏览器 WASM 宿主验证：相同核心代码与显式资源能否产生有效 PDF，需记录构建模式、资源装载、产物大小、启动时间、内存、限制及实际输出。浏览器仅作为运行宿主，不使用 DOM/浏览器排版完成 PDF。通过服务器代生成、启动另一个排版引擎或仅导出一个空模块均不算通过。

WASM 可行性结果应在大量新内容能力开发前得到。失败时输出可重现原因与对接口/发布范围的影响，不把一个不通过的试验包装成支持。WASM 正式交付不是本首版默认承诺，但其失败不能不经讨论就无限延期。Rust/Go/Python 绑定仍保留在后续路线，不实现第二套排版核心。

## 5. 真实文档验收集

第一项实施工作是建立文档基线，不先改引擎。验收集分为两类，防止绿色 CI 掩盖未实现的功能：

- **基线样本**：只使用 M12 已支持能力，冻结输入、字体指纹、配置、参考 PDF、提取文字、页面图像和同环境哈希。此类回归必须一直通过。
- **目标样本**：含预览版计划支持的列表、强调、图片、表格和页码。当前可明确记录为未支持；它们未转成真实通过之前，不能宣布预览版验收完成。不得将其 expected-error 或跳过状态计为功能通过。

建议案例清单：

| 案例 | 检查目的 | 必须交付的证据 |
| --- | --- | --- |
| 双语简报 | 标题、中文/英文正文、信息面板、长短内容 | 文字不丢失、可复制、正确字体/颜色/边界，人工审阅的页面图 |
| 完整业务报告 | 强调、两级列表、图像、明细表、页码 | 每个新能力有独立断言，最终整份报告无重叠、截断或幽灵页 |
| 明细增长变体 | 同一模板使用 10/30/100 条合成记录 | 行内容不重不漏，跨页表头重复，过高行明确错误而非卡住 |
| 长报告与极限输入 | 超长段落、零宽/过宽内容、页数与资源额度 | 正常案例成功；异常案例在预期位置失败且不写出半成品 |
| 跨入口/平台 | 同一份输入经 CLI、.NET 及目标平台执行 | 文字和几何一致；同环境确定性结果保持，差异有证据和解释 |

样本的精确页数与几何期待值必须在作者编写样本后，经独立检查和人工审阅冻结，不能把当前引擎输出直接自动抄成真值，也不能在本设计尚未渲染样本时捏造页数。

独立验证可复用现有 PDF 检查、文本提取和 Chrome 对照方法。位图差异只是证据之一，不设置一个掩盖错误的全局宽松阈值。固定字体、同工具链的未改动基线要求字节一致；跨系统字体压缩/构建差异使用单独的平台基线并检查文字和几何，不把全平台哈希相同当作唯一条件。

字体作为显式测试资源记录授权来源和指纹，不向用户分发字体文件。模板、合成数据与允许分发的图片可以进入样例产物。

## 6. 性能预算与发布验收

分别测量冷启动、热转换延迟/吞吐、累计托管分配、进程峰值内存、输出大小与多任务隔离。输入解析、字体/图像资源装载、布局、序列化应尽可能分段记录；不要再将一个长段落布局的分配比例当作全流程性能指标。

基准记录固定提交、构建模式、机器/系统、字体资源、输入、样本次数和原始数据。建议先在指定参考机器上采集不少于 10 次独立冷启动与 30 次热转换，并重复批次；这些是测量方法建议，不是现有结果。共享 CI 的时间波动只作为警报，需稳定复现才判断退化。

本稿不虚构绝对毫秒、RSS 或 QPS 保证。第一项基线工作必须输出参考机器上的实际测量与候选预算，经过审阅后作为预览版退出条件；未设定或未通过预算时，不得对外宣传已经达到“超高性能”。任何后续优化必须指出具体工作负载、瓶颈占比、改善指标和兼容性代价。

首版验收同时要求：报告目标案例真实成功、完整失败路径、独立页面检查、目标平台实际运行、从干净环境复现接入、明确支持矩阵、可检索诊断说明与通过审阅的资源/性能预算。已有 NUnit 数量、一次 PR 绿色状态或样例截图都不能代替这些条件。

## 7. 推荐交付顺序，而非一次性实施清单

| 顺序 | 工作包 | 退出条件 | 主要非目标 |
| --- | --- | --- | --- |
| A | 文档验收基线与支持矩阵 | 基线/目标案例分离，独立检查方法、初始测量与预算提案可审阅 | 不改引擎，不恢复微优化 |
| B | 接入与 WASM 风险验证 | Node/CLI 和浏览器 WASM 分别有可重复的通过/失败证据及影响结论 | 不宣布 SDK/WASM 已发布 |
| C | 报告文字表达 | 显式粗体资源、列表分别通过自己的案例与兼容性检查 | 不同时做完整字体样式系统 |
| D | 显式静态图像 | 受限 JPEG 在页面中正确绘制；资源和错误边界通过 | 不引入自动网络读取 |
| E | 表格先单页、后跨页 | 先列宽/单元格，再整行分页/重复表头，分别独立验收 | 不做通用浏览器表格布局 |
| F | 完整报告分页体验 | 页码、受控页眉页脚、标题随段；组合报告可审阅 | 不做完整 CSS Paged Media |
| G | 开发者预览交付检查 | CLI/.NET 接入、Linux/Windows AOT、样例、诊断、预算与发布门槛全部核验 | 不自动公开发布 |

一个工作包可能需要多个小 PR，例如字体与列表、两个可行性验证、单页表格与跨页表格。每个都顺序进行：明确设计/验收 → 测试先行 → 实现 → 独立审查 → 修复 → 合并 → 实际 main 验证。前一实现未合并和验证，不创建下一实现 PR。

以前建议的 M13“PDF 文本十六进制编码低分配优化”移入性能候选池。仅当验收负载的测量表明它是值得优先处理的瓶颈，再决定是否执行。待范围稿与 A 的实施计划审阅后，再将下一个编号分配给真实交付；本次不预占 M13 或连续生成 M14/M15。

## 8. 下一步与需要审阅的新取舍

本稿需要审阅的是新增产品边界，而不是重新询问已授权的逐阶段合并：双语报告为主场景；JPEG 优先、PNG 后续；受限整行分页表格；CLI/.NET 与 Linux/Windows x64 AOT 为首发目标；WASM 较早验证但暂不承诺同批发布。

范围确认后，只展开工作包 A 的实施计划和首批案例清单；其他工作包保持路线图状态。没有一次批准整个未知实现，也不把新需求隐含在某个“性能优化”PR 中。

过程状态应只给出当前交付物、准确提交、真实阻塞或本阶段完成结论。没有状态变化时不靠密集轮询制造进展；不得在本次操作结束后声称仍在后台持续开发。进度更新与开发事实分开。
